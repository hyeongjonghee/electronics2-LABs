1. 실험 1 · 4비트 곱셈기 (mult_4bit)

① 목적

4비트 수 두 개를 곱해 8비트 결과를 내는 조합회로를 만들고, 256개 입력 조합 전체에서 결과가 맞는지 Vivado 시뮬레이션으로 확인한다.

② 이론

4비트 부호 없는 수의 최대 곱은 \(15 \times 15 = 225 < 2^8\)이라 결과는 8비트면 충분하다. 곱셈은 세로 곱셈과 같이 부분곱을 더해 만든다 [1].

$$P = A\cdot B = \sum_{i=0}^{3} b_i\,(A\cdot 2^{i})$$

③ 포트 · 보드 매핑과 교재 대조

교재 「Combo II DLD 장비를 이용한 디지털 논리 회로 설계」 2.3절 p.321의 핀표와 한 줄씩 대조했다. 16개 핀 모두 일치한다.

신호교재 p.321우리 XDC판정
a[3:0]Y1 · W3 · U2 · T1 (DIPSW_1~4)sw[7:4] → Y1 · W3 · U2 · T1일치
b[3:0]W4 · W1 · V4 · U4 (DIPSW_5~8)sw[3:0] → W4 · W1 · V4 · U4일치
m[7:0]L4 · M4 · M2 · N7 · M7 · M3 · M1 · N5 (LED1~8)led[7:0] → 같은 순서일치
I/O 표준LVCMOS33LVCMOS33일치

2. 실험 2 · BCD → 이진수 변환 (bcd_conv)

① 목적

십의 자리와 일의 자리 BCD(각 0~9)를 하나의 이진수(0~99)로 바꾸고, 자리가 0~9를 벗어나면 valid를 0으로 내린다.

② 이론

$$N = 10\,T + O,\quad 0 \le N \le 99 < 2^7,\qquad \text{valid} = (T\le 9)\land(O\le 9)$$

입력 256개 중 유효 100개, 무효 156개다. 무효 입력에서도 bin은 \(10T+O\)의 아래 7비트, 즉 128로 나눈 나머지가 나온다. 예를 들어 (15, 15)는 \(165 \bmod 128 = 37\)이다.

③ 포트 · 보드 매핑과 교재 대조 (수정함)

교재 「Combo II DLD 장비를 이용한 디지털 논리 회로 설계」 2.2절 p.245의 핀표와 대조한 결과, 입력은 일치했지만 출력이 LED 한 칸씩 어긋나 있었다. 교재에는 valid 출력이 없는데, 실험 전에는 수업 코드가 추가한 valid를 LED1에 놓고 bin을 LED2~8로 밀어 두었기 때문이다. bin을 교재대로 LED1~7에 두고 valid를 남는 LED8로 옮겼다.

신호교재 p.245실험 전수정 후

bin[6:0]LED1~7 (L4 · M4 · M2 · N7 · M7 · M3 · M1)LED2~8LED1~7
valid(없음)LED1LED8 (N5)

3. 실험 3 · STM32 Hello World와 STM32_0 과제1

① 목적

NUCLEO-G474RE에 프로그램을 올려 PC로 Hello, World!를 출력하는 것을 확인하고, 버튼(PC13)을 누를 때마다 내장 LED(PA5)의 상태 변경 간격이 1 → 2 → 4 → 8 → 1 s로 바뀌게 한다.

② 동작 원리

Hello World. 수업 템플릿의 main.c(112행)가 초기화 직후 printf("Hello, World!\n");를 한 번 호출한다. printf는 ece2_474_stdio.c를 거쳐 UART2로 나가고, UART2는 보드 안에서 ST-LINK의 가상 COM 포트(USB)에 연결되어 있다. 그래서 과제 코드와 상관없이 RESET할 때마다 한 줄이 출력된다.

과제1. 메인 루프가 polling_routine()을 계속 호출하고, 함수는 매번 ① 버튼이 방금 눌렸는지 ② 마지막 LED 변경 뒤 간격만큼 지났는지를 확인한다. 둘을 잇는 것이 변수 interval_ms다. HAL_GetTick()은 1 ms마다 1씩 느는 카운터다 [2].

$$\text{now} - \text{last} \ge \text{interval} \Rightarrow \text{LED 반전},\qquad \text{press} = (\text{cur}=1)\land(\text{prev}=0)\land(\text{now}-\text{last\_press}\ge 200\ \text{ms})$$

③ 핀

④ 핵심 코드

void polling_routine(void)
{
    static uint32_t last_ms = 0;              // 마지막으로 LED를 바꾼 시각
    static uint32_t interval_ms = 1000U;      // 지금 간격 (처음은 1초)
    static GPIO_PinState previous = GPIO_PIN_RESET;  // 직전 버튼 상태
    static uint32_t last_press_ms = 0;        // 마지막으로 버튼을 인정한 시각

    uint32_t now_ms = HAL_GetTick();          // 지금 시각 (ms)
    GPIO_PinState current = HAL_GPIO_ReadPin(BUTTON_ece2_GPIO_Port, BUTTON_ece2_Pin);

    /* ① 버튼 확인: 방금 눌린 순간이면 간격을 다음 값으로 */
    if (current == GPIO_PIN_SET && previous == GPIO_PIN_RESET
        && now_ms - last_press_ms >= 200U)
    {
        last_press_ms = now_ms;
        if (interval_ms >= 8000U)
        {
            interval_ms = 1000U;              // 8초 다음은 1초로 돌아감
        }
        else
        {
            interval_ms = interval_ms * 2U;   // 1→2→4→8초
        }
    }
    previous = current;

    /* ② 시계 확인: 간격만큼 지났으면 LED 반전 */
    if (now_ms - last_ms >= interval_ms)
    {
        last_ms = now_ms;
        HAL_GPIO_TogglePin(LED_ece2_GPIO_Port, LED_ece2_Pin);
    }
}

⑤ 모의 실행 (실험 전 결과)

위 함수를 저장소 파일에서 그대로 잘라 PC의 gcc로 실행하고, HAL 함수 세 개만 가짜 시계·버튼으로 바꿨다. 버튼을 1.5 s 누르고 있기, 채터링 2회를 포함한 시나리오에서 간격 열은 1 s×10 → 2 s×10 → 4 s×7 → 8 s×5 → 2.05 s×1 → 1 s×14로 기대와 같았다.

⑧ 조교 디버거 시연 · 중단점과 변수 값 변경

시연 중 조교가 VS Code의 STM32Cube 디버거로 다음을 보여 주었다.

  1. polling_routine() 안에 중단점(breakpoint)을 걸어 실행 중인 CPU를 그 줄에서 멈췄다.
  2. 멈춘 상태에서 디버거의 변수 창으로 interval_ms를 1000에서 200으로 바꿨다.
  3. 실행을 이어 가자, 코드를 다시 빌드하거나 다운로드하지 않았는데도 LED 간격이 1 s에서 200 ms로 바뀌었다.

왜 바로 바뀌는가. interval_ms는 함수 안의 static 변수라 호출이 끝나도 값이 RAM에 남는다. 디버거는 ST-LINK(SWD)로 CPU를 멈추고 RAM을 직접 읽고 쓸 수 있으므로, 그 칸의 값만 바꾸면 다음 호출부터 ② 시계 확인의 비교 기준이 200이 된다. 노래를 일시정지하고 템포 숫자만 바꾼 뒤 다시 재생하는 것과 같다.

확인한 사실. 시연 뒤 PC의 ece2_474_routine.c를 보관본과 비교했더니 14:44:49(과제2를 올린 시각) 이후 바뀐 줄이 없었다. 따라서 이 변경은 소스 코드가 아니라 실행 중인 보드의 RAM에서 일어난 것이다.

원리상 따라오는 것(직접 확인하지는 않음). 바뀐 값은 플래시에 저장되지 않는다. RESET이나 전원을 다시 넣으면 시작 코드가 초깃값 1000을 RAM에 다시 복사하므로 1 s로 돌아간다. 디버거로 값을 바꿔 보는 방법은 코드를 고치고 빌드·다운로드를 반복하지 않고 "이 값이면 어떻게 동작할까"를 빠르게 시험하는 데 쓰인다.

4. 실험 4 · STM32_0 과제2 — 외부 LED (PB0)

① 목적

과제1과 같은 동작을 PB0에 연결한 외부 LED로 보인다.

② 회로와 코드 변경

PB0 → 저항 → LED(+) / LED(−) → GND로 연결한다. PB0이 HIGH(3.3 V)이면 LED가 켜진다.

$$I \approx \frac{3.3 - V_F}{R},\qquad V_F \approx 2.0\ \text{V}:\ \ R=330\,\Omega \Rightarrow 3.9\ \text{mA},\ \ R=1\,\text{k}\Omega \Rightarrow 1.3\ \text{mA}$$ 
- HAL_GPIO_TogglePin(LED_ece2_GPIO_Port, LED_ece2_Pin);
+ HAL_GPIO_TogglePin(GPIO_OUT1_ece2_GPIO_Port, GPIO_OUT1_ece2_Pin);  /* 과제2: PB0 외부 LED */

③ 모의 실행

같은 시나리오에서 LED 변경 47번이 모두 GPIOB(PB0)에서 일어났고 GPIOA(PA5)는 바뀌지 않았다. 간격 열은 1 s×10 → 2 s×10 → 4 s×7 → 8 s×5 → 2.05 s×1 → 1 s×14로 과제1과 같다.

④ 보드 검증

배선: A3(PB0) → 저항(330 Ω~1 kΩ) → LED 긴 다리(+), LED 짧은 다리(−) → GND(CN6). 보드 USB를 뺀 상태에서 배선

5. 고찰

  • 핀 번호가 맞아도 배치는 다를 수 있다. BCD 변환은 핀 번호 16개가 모두 교재와 같은 집합이었지만, 어떤 신호를 어느 LED에 두는지가 한 칸 어긋나 있었다. 수업 코드에 교재에 없는 valid 출력이 추가되면서 생긴 차이다. 빌드 성공이나 핀 일치만으로는 이런 차이가 드러나지 않으므로, 교재 핀표를 신호 이름 단위로 대조해야 한다.
  • 테스트벤치가 보는 범위. 수업 TB는 안쪽 모듈만 검사해서, 최상위 연결을 바꿔도 PASS가 그대로 나온다. 실제로 BCD 출력 배치를 바꾼 뒤에도 수업 TB는 아무것도 알려 주지 않았다. 최상위 모듈을 256가지로 검사하는 tb_top을 추가해 이 빈틈을 메웠다.
  • 빌드 도구는 파일 시각으로 판단한다. 보관해 둔 과제1 파일을 PowerShell Copy-Item으로 되돌렸더니 Ninja가 "no work to do"라며 다시 컴파일하지 않았다. 복사가 원래 수정 시각(과제1을 만든 10/07)을 유지해, 마지막 빌드(과제2)보다 오래된 파일로 보였기 때문이다. 그대로 올렸다면 과제2 프로그램이 들어갔을 것이다. 파일 시각을 현재로 갱신한 뒤 다시 빌드해 ELF 시각이 바뀐 것을 확인하고 올렸다.
  • 8 s → 1 s 전환의 즉시 반전. 간격을 줄이는 순간 이미 새 간격보다 오래 기다린 상태라면 LED가 누르자마자 한 번 바뀐다. 과제 조건은 만족하는 설계상 동작이며, 모의 실행(그림 3-1의 2.05 s 구간)에서 미리 예측했다.
  • 디버거로 바꾼 값은 소스에 남지 않는다. 조교 시연에서 interval_ms를 디버거로 200으로 바꾸자 LED가 즉시 200 ms로 깜빡였지만, 소스 파일은 바뀌지 않았다. 디버거는 빠르게 실험해 보는 도구이고, 원하는 값을 찾았다면 결국 코드에 반영해 다시 빌드해야 다음 실행에서도 유지된다.
  • Hello World의 위치. printf는 과제 코드가 아니라 main.c에 있어 어떤 과제를 올려도 시작할 때 한 번 출력된다. 그래서 과제1 프로그램 하나로 Hello World와 과제1을 함께 시연할 수 있었다.
