1. STM32_2 제공 예제 ① · ② — PC와 MCU의 문자 입출력

① 목적

예제 ①은 PC의 Serial Monitor에서 보낸 글자를 MCU가 getchar()로 받아 그대로 다시 출력한다. 예제 ②는 받은 글자 한 바이트를 UART3(PC10)로 FPGA 쪽에 보내고, 송신 함수가 돌려준 결과 코드를 출력한다. 이후 과제 5 ~ 7은 모두 이 두 예제를 바탕으로 한다.

② 이론

getchar()는 HAL_UART_Receive(&huart2, …, HAL_MAX_DELAY)로 이어져, 글자가 올 때까지 그 자리에서 기다린다. 화면이 조용한 것은 멈춘 것이 아니라 기다리는 상태다. 예제 ②의 HAL_UART_Transmit 결과 HAL_OK = 0은 "MCU가 마지막 비트까지 내보냈다"는 뜻일 뿐, 받는 쪽이 받았다는 확인이 아니다. UART에는 수신 확인 응답이 없기 때문이다.

$$t_{bit}=\frac{1}{9600}=104.17\ \mu\text{s},\qquad \text{한 글자}=10\,t_{bit}=1.042\ \text{ms (시작 1 + 데이터 8 + 정지 1)}$$

③ 코드 (polling_routine)

예제 ①

void polling_routine(void)
{
    int ch = getchar();
    if (ch != EOF)
    {
        printf("받은 문자: %c\r\n", ch);
    }
}

2. STM32_2 과제5 — PC → MCU → PC (글자와 바이트 값 출력)

① 목적

PC에서 보낸 글자 한 개를 MCU가 받아, 그 글자와 바이트 값(16진수)을 함께 출력한다. 키보드 글자가 실제로는 ASCII 숫자 한 바이트로 전송된다는 것을 확인한다.

② 이론

숫자 글자 '0'~'9'는 0x30 ~ 0x39, 대문자는 0x41부터, 소문자는 대문자 + 0x20이다. 그래서 글자 '1'(0x31)과 숫자 1(0x01)은 서로 다른 값이다. %02X는 16진수 대문자 두 자리로 찍는 형식이다. 화면에 찍히지 않는 제어 문자(0x20 미만 · 0x7F 이상)는 글자 대신 "(제어 문자)"로 표시한다.

③ 코드

void polling_routine(void)
{
    int ch = getchar();                 /* 입력이 올 때까지 여기서 기다림(멈춘 것이 아님) */
    if (ch != EOF)                      /* EOF(-1) = 수신 오류. 정상 문자만 처리 */
    {
        uint8_t data = (uint8_t)ch;     /* 0~255 한 바이트로 변환 */
        if (data >= 0x20U && data <= 0x7EU)
        {
            /* 화면에 찍히는 문자(공백~'~')는 문자와 값을 함께 출력 */
            printf("받은 문자: '%c'  바이트 값: 0x%02X\r\n", (char)data, (unsigned int)data);
        }
        else
        {
            /* 줄바꿈(0x0D, 0x0A) 같은 제어 문자는 값만 출력 */
            printf("받은 문자: (제어 문자)  바이트 값: 0x%02X\r\n", (unsigned int)data);
        }
    }
}

3. STM32_2 과제6 — PC → MCU → FPGA → PC (여러 글자)

① 목적

PC가 MCU에 보낸 글자를 MCU가 UART3(PC10)로 FPGA에 넘기고, FPGA(uart_cmd_top)는 받은 글자를 자기 USB-UART(F6)로 PC에 다시 보낸다. PC에서 COM5(MCU)와 COM6(FPGA)를 함께 열어, 보낸 문자열과 FPGA가 받은 문자열이 같은지 비교한다. 조교 요구에 따라 여러 글자를 한 번에 보내도 빠짐없이 전달되어야 한다.

② 이론 — 왜 첫 판은 여러 글자를 놓쳤나

첫 판(아래 왼쪽)은 getchar()로 한 글자를 받은 뒤, UART3 전송(1 ms)과 결과 printf(약 40바이트 ≈ 42 ms)를 마치고 나서야 다음 글자를 받으러 간다. 그런데 Serial Monitor는 문자열을 쉬지 않고 보내므로 다음 글자가 1.04 ms 뒤에 도착한다. UART2 수신 레지스터는 한 바이트만 담으므로, 기다려 주는 쪽이 없으면 뒤 글자가 앞 글자를 덮어쓰고(오버런) HAL은 오류 상태가 된다. 그래서 "1Aa"를 한 번에 보내면 앞 글자만 전달됐다.

$$\underbrace{1.04\ \text{ms}}_{\text{다음 글자 도착}}\ \ll\ \underbrace{1.04\ \text{ms}+\approx 42\ \text{ms}}_{\text{첫 판이 한 글자에 쓰는 시간}}$$

수정판(v2)은 받기와 처리를 나누었다. ① UART2 수신 인터럽트가 바이트가 올 때마다 바로 링 버퍼(256바이트)에 넣고 다음 수신을 다시 요청한다(수 µs). ② 메인 루프는 버퍼에서 하나씩 꺼내 UART3로 보낸다. 들어오는 속도와 나가는 속도가 모두 9600 bps라 버퍼가 쌓이지 않는다. ③ 결과 출력은 20 ms 동안 새 바이트가 없을 때(한 묶음이 끝났을 때) 한 줄로만 한다. 오류가 나면 HAL이 수신을 멈추므로 HAL_UART_ErrorCallback에서 수신을 다시 시작한다.

링 버퍼의 head는 인터럽트만, tail은 메인 루프만 바꾼다. 8비트 인덱스는 한 번에 읽고 쓰이므로 두 쪽이 서로의 값을 깨뜨리지 않고, 256에서 자연히 0으로 돌아간다(가득 참 = head+1 == tail, 최대 255바이트).

③ 코드 (첫 판 → 수정판)

첫 판 · task6_v1_single

void polling_routine(void)
{
    int ch = getchar();
    if (ch != EOF)
    {
        uint8_t data = (uint8_t)ch;
        /* 1바이트 송신, 최대 100 ms 대기. 결과 0(HAL_OK)은 "MCU가 다 보냈다"는 뜻일 뿐,
         * FPGA가 받았는지는 FPGA 쪽 COM 포트 출력으로 따로 확인합니다. */
        HAL_StatusTypeDef result = HAL_UART_Transmit(&huart3, &data, 1U, 100U);
        if (data >= 0x20U && data <= 0x7EU)
        {
            printf("FPGA로 보냄: '%c' (0x%02X)  전송 결과: %d\r\n",
                   (char)data, (unsigned int)data, (int)result);
        }
        else
        {
            printf("FPGA로 보냄: (제어 문자) (0x%02X)  전송 결과: %d\r\n",
                   (unsigned int)data, (int)result);
        }
    }
}

수정판 · 링 버퍼와 수신 인터럽트

/* 여러 글자를 한 번에 받아도 놓치지 않도록 PC 수신 바이트를 모아 두는 링 버퍼(256바이트).
 * 인터럽트(uart2_isr_p6)가 넣고, 메인 루프(polling_routine)가 꺼냅니다.
 * head는 ISR만, tail은 메인 루프만 바꾸므로 8비트 인덱스 하나씩이면 충돌하지 않습니다. */
#define RX_BUF_SIZE 256U
static volatile uint8_t rx_buf[RX_BUF_SIZE];
static volatile uint8_t rx_head = 0U;   /* 다음에 넣을 위치 (ISR) */
static volatile uint8_t rx_tail = 0U;   /* 다음에 꺼낼 위치 (메인 루프) */
static volatile uint32_t rx_overflow = 0U;
static void uart2_isr_p6(void)
{
    /* 받은 1바이트를 링 버퍼에 넣고 바로 다음 수신을 요청합니다(짧게 끝냄). */
    uint8_t next = (uint8_t)(rx_head + 1U);
    if (next != rx_tail)
    {
        rx_buf[rx_head] = uart2_rx_ece2;
        rx_head = next;
    }
    else
    {
        rx_overflow++;   /* 버퍼가 가득 참: 이 바이트는 버림 */
    }
    HAL_UART_Receive_IT(&huart2, &uart2_rx_ece2, 1U);
}
/* 수신 중 오버런·잡음 등 오류가 나면 HAL이 수신을 멈추므로, 여기서 다시 시작합니다. */
void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART2)
    {
        HAL_UART_Receive_IT(&huart2, &uart2_rx_ece2, 1U);
    }
}

void polling_routine(void)
{
    static char line[RX_BUF_SIZE + 1U];
    static uint32_t count = 0U;
    static uint32_t fail = 0U;
    static uint32_t last_ms = 0U;     /* 마지막으로 바이트를 꺼낸 시각 */

    if (rx_tail != rx_head)
    {
        uint8_t data = rx_buf[rx_tail];
        rx_tail = (uint8_t)(rx_tail + 1U);
        last_ms = HAL_GetTick();
        if (HAL_UART_Transmit(&huart3, &data, 1U, 100U) != HAL_OK)
        {
            fail++;
        }
        if (count < RX_BUF_SIZE)
        {
            /* 화면에 찍히지 않는 제어 문자(CR·LF 등)는 '.'로 표시 */
            line[count] = (data >= 0x20U && data <= 0x7EU) ? (char)data : '.';
            count++;
        }
    }
    else if (count > 0U && (HAL_GetTick() - last_ms) >= 20U)   /* 20 ms 동안 새 바이트 없음 = 한 묶음 끝 */
    {
        line[count] = '\0';
        printf("FPGA로 보냄: \"%s\" (%lu바이트, 전송 실패 %lu, 버퍼 넘침 %lu)\r\n",
               line, (unsigned long)count, (unsigned long)fail, (unsigned long)rx_overflow);
        count = 0U;
        fail = 0U;
    }
}

FPGA 회로 uart_cmd_top(수신 → 송신 되돌림 + 명령 해석)은 실험 전 보고서 6장 ④와 같고 수정하지 않았다.

처음에는 MCU의 전송 결과가 0인데도 FPGA COM6에 0바이트가 오거나, 의미 없는 바이트가 무작위로 왔다. 오실로스코프로 보면 PC10 파형은 정상이었다. 원인을 하나씩 좁힌 과정은 다음과 같다.

단계확인한 것결과 · 판단
1COM6이 PC에 보이지 않음FTDI 드라이버의 "Load VCP"가 꺼져 있었다. 장치 관리자에서 켜자 COM6 생성. JTAG(Xilinx Platform Cable)은 별도 장치라 비트스트림은 정상으로 올라갔다.
2PC10 파형 (오실로스코프)'U'(0x55)를 반복 전송해 주파수 4.771 kHz 측정 → 비트 폭 \(1/(2\times4771)=104.8\ \mu\text{s}\), 약 9542 bps. 9600 bps 대비 −0.6 %로 정상 범위.
3CLOCK SELECT 다이얼50 MHz 위치가 아니었다. FPGA 수신기의 비트 폭 계산(5208클록)은 50 MHz를 전제로 하므로, 다이얼을 맞춘 뒤 UART가 맞기 시작했다.
4PORT A ENABLE 스위치 (DIP SW5의 2번)ON이면 LED에 엉뚱한 값이 무작위로 바뀌고, OFF로 바꾸자 정확한 값이 왔다. 두 번 바꿔 보아 같은 결과를 확인했다. 확장 포트와 FPGA 사이의 버스 스위치(PI3C3245)는 활성 LOW 입력(풀다운 4.7 kΩ)이라 OFF = 연결이다. ON이면 F8이 떠(floating) 잡음을 바이트로 읽었다.

4. STM32_2 과제7 — UART 명령으로 FPGA LED 제어

① 목적

FPGA가 받은 글자를 명령으로 해석해 LED1을 제어한다: '0' 끄기, '1' 켜기, '2' 반전, 그 밖의 글자는 그대로 둔다. "켜기"를 반복하면 계속 켜져 있고 "반전"을 반복하면 매번 바뀌는지 확인한다. LED2 ~ 8에는 마지막으로 받은 바이트의 아래 7비트를 표시한다.

② 이론

$$lamp_{next}=\begin{cases}0 & rx=\text{0x30 ('0')}\\ 1 & rx=\text{0x31 ('1')}\\ \overline{lamp} & rx=\text{0x32 ('2')}\\ lamp & \text{그 밖}\end{cases}$$

켜기는 현재 상태와 상관없이 1로 정하고, 반전은 현재 상태를 뒤집는다. 판단은 FPGA가 한다. MCU는 과제6 수정판과 같은 방식으로 모든 바이트를 넘기고, 한 묶음이 끝나면 "이 명령들을 차례로 적용하면 LED1이 어떻게 되어야 하는지"를 참고로 출력한다.

③ 코드 (과제6 수정판과 다른 부분)

    static uint8_t expect_led = 0U;   /* FPGA 리셋 직후 0이라고 가정 */

        else if (data == '1') expect_led = 1U;
        else if (data == '2') expect_led ^= 1U;
    ...
        printf("명령 \"%s\" (%lu바이트) -> 예상 LED1: %s  (전송 실패 %lu, 버퍼 넘침 %lu)\r\n",

5. FPGA 실습 ① 서보모터 제어 (servo_ctrl)

6. FPGA 실습 ② SRAM 읽기 · 쓰기 (sram)

① 목적

외부 SRAM 칩의 주소 0 ~ 15에 DIP 스위치로 정한 4비트 값을 쓰고, 같은 주소에서 다시 읽어 LED5 ~ 8로 확인한다. FPGA와 SRAM이 16비트 데이터선을 번갈아 쓰는 방법, 즉 쓸 때는 FPGA가 값을 내고 읽을 때는 손을 떼는(Z) 방법을 익힌다.

② 이론

CS · WE · OE는 모두 LOW 활성이다. 쓰기: CS = 0, WE = 0, FPGA가 데이터선 구동. 읽기: CS = 0, OE = 0, FPGA는 Z, SRAM이 구동. 두 버튼을 함께 누르면 둘 다 무시한다.

보드의 칩은 Samsung K6R4016V1D(256K × 16, 3.3 V)이다. 데이터시트에 따르면 쓰기는 "CS나 WE 중 먼저 HIGH가 되는 순간" 끝나고 그때 데이터선 값이 저장되며, 데이터 홀드 시간 \(t_{DH}\)의 최소값은 0 ns이다[2]. 실험 전에 ISSI 칩 모델로 검토한 결론(교재 회로는 WE 상승과 데이터 Z가 같은 순간이라 여유 0)이 이 칩에도 그대로 적용된다. 보드용 최상위는 WE를 올린 뒤 데이터를 2클록(40 ns) 더 유지한다.

$$t_{DH}^{\text{교재}}=0\ \text{ns (경쟁)},\qquad t_{DH}^{\text{보드용}}=2\times 20\ \text{ns}=40\ \text{ns}\ \ge\ 0\ \text{ns}$$

// 동시 요청 무시, 미사용 시 Z, LED 표시는 수업 sram과 같다.

module sram_board_top #(parameter integer HOLD_CYCLES = 2)(
    input  wire clk_50mhz,
    input  wire ctrl_w, ctrl_r,
    input  wire [3:0] address, data_in,
    output wire ram_cs, ram_oe, ram_we,
    output wire [17:0] ram_address,
    inout  wire [15:0] ram_data,
    output wire [7:0] led_out
);
    (* ASYNC_REG = "TRUE" *) reg [1:0] w_sync = 2'b00, r_sync = 2'b00;
    reg [3:0] hold = 0;
    always @(posedge clk_50mhz) begin
        w_sync <= {w_sync[0], ctrl_w};
        r_sync <= {r_sync[0], ctrl_r};
    end
    wire drive_req, read_req, cs_unused, oe_unused, we_unused;
    // 수업 버스 제어 모듈을 동기화된 버튼으로 그대로 사용(동시 요청 무시 규칙 유지)
    sram_bus_control u_control(w_sync[1], r_sync[1], drive_req, read_req, cs_unused, oe_unused, we_unused);
    always @(posedge clk_50mhz)
        if (drive_req) hold <= HOLD_CYCLES;
        else if (hold != 0) hold <= hold - 1'b1;
    wire drive_data = drive_req || (hold != 0);          // 쓰기 끝난 뒤에도 데이터 유지
    wire read_data  = read_req && (hold == 0);           // 데이터 해제 후에만 읽기
    assign ram_we = !drive_req;
    assign ram_oe = !read_data;
    assign ram_cs = !(drive_data || read_data);
    assign ram_address = {14'b0, address};
    assign ram_data = drive_data ? {12'b0, data_in} : 16'bz;
    assign led_out = read_data ? {4'b0, ram_data[3:0]} : 8'b0;
endmodule

7. FPGA 실습 ③ DAC (dac)

① 목적

8비트 병렬 DAC 칩에 0, 1, …, 255, 0, …을 10 ms마다 차례로 써서 계단 모양의 톱니파를 만들고, 오실로스코프로 디지털 값이 아날로그 전압으로 바뀌는 것을 확인한다.

② 이론

$$V_{out}=V_{ref}\cdot\frac{D}{256},\qquad T_{ramp}=256\times\frac{500\,000}{50\ \text{MHz}}=256\times 10\ \text{ms}=2.56\ \text{s}$$

보드용 dac_board_top은 쓰기 펄스(WR LOW)를 2클록(40 ns)으로 늘려 AD7302의 최소 20 ns 조건에 여유를 두었다(실험 전 보고서 3장).

8. 고찰

  1. "전송 결과 0"은 통신 성공이 아니다. 예제 ② · 과제6 내내 MCU는 결과 0(HAL_OK)을 냈지만, FPGA는 0바이트를 받거나 잡음을 받았다. UART에는 수신 확인이 없으므로, 받는 쪽의 결과(FPGA가 되돌려 보낸 COM6 출력과 LED)로만 성공을 판단할 수 있었다. 과제6을 "FPGA가 받은 글자를 다시 PC로 보내는" 구조로 만든 것이 원인을 찾는 데 결정적이었다.
  2. 보드 설정도 회로의 일부다. 같은 비트스트림 · 같은 코드인데 결과를 바꾼 것은 CLOCK SELECT 다이얼(50 MHz)과 PORT A ENABLE 스위치(OFF = 연결)였다. 실험 전 보고서는 ENABLE을 ON으로 적었는데, 이름만 보고 판단한 것이었다. 버스 스위치의 활성 LOW 입력처럼 스위치의 의미는 회로도로 확인해야 한다. 원인을 좁힐 때는 오실로스코프로 MCU 쪽 파형이 정상(9542 bps, 3.2 V)임을 먼저 확인해, 문제를 FPGA 쪽 연결로 한정할 수 있었다.
  3. 기다리는 입력(블로킹)과 인터럽트 입력. getchar 방식은 한 글자를 처리하는 동안(printf ≈ 42 ms) 다음 글자를 받을 수 없어, 1 ms 간격으로 이어 오는 문자열을 놓쳤다. 실험 전 보고서 고찰 6에서 예상한 한계가 조교의 여러 글자 요구로 그대로 드러났다. 수신 인터럽트가 바이트를 링 버퍼에 넣기만 하고 바로 돌아오게 하자, 처리 시간이 길어도 입력을 잃지 않았다. 출력은 20 ms 동안 입력이 없을 때 한 번만 해서, 출력이 다음 입력과 겹치는 시간도 줄였다.
  4. 클록이 서로 다른 두 장치의 UART. 실측 MCU 비트 폭 104.8 µs(9542 bps)와 FPGA 수신기 9600.6 bps는 0.6 % 차이다. 글자 하나(10비트) 동안 쌓이는 어긋남은 6 %의 비트 폭으로 허용치(반 비트, 50 %)보다 훨씬 작고, 시작 비트마다 다시 맞추므로 연속 전송에서도 쌓이지 않는다. 연속 14바이트 TB가 이것을 확인했다.
  5. 교재 핀표는 신호 이름과 칩 기준으로 읽는다. 서보는 임시 핀(E8)을 교재 핀(AA22)으로, SRAM은 p.603 표로 37핀을 채웠다. 표에 UB/LB가 없다는 것은 보드에서 GND에 고정되었다는 뜻이므로, 최상위에서 포트를 지웠다. DAC 표의 클록 N8은 LAB5에서처럼 키패드 핀이라 B6로 바로잡았다. 또 PC로 보낸 파일이 실제로 바뀌었는지(크기) 확인하지 않아 빌드를 한 번 날렸다. 빌드 전에 입력 파일을 확인하는 습관이 필요하다.
  6. 오실로스코프 시간축은 신호의 주기에 맞춘다. DAC 톱니는 주기 2.56 s라 2 ms/칸에서는 한 계단도 다 못 보아 "계속 올라가기만" 보였다. 반대로 UART 비트(104 µs)는 4 µs/칸에서 에지 하나만 보였다. 먼저 계산한 주기로 시간축을 정하면(주기 ÷ 10칸) 한 번에 원하는 모양을 볼 수 있다.
  7. 화면 표시와 실제 데이터를 구분한다. Serial Monitor의 한글 깨짐은 9600 bps에서 UTF-8 3바이트가 나뉘어 들어와 생긴 표시 문제였다. 같은 출력이 PC 모의 실행에서는 정상이고, 영문 · 16진수 부분은 맞게 보였으므로 MCU 코드 문제가 아님을 알 수 있었다.
